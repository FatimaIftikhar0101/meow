| 39 | **The ledger was single-entry while the schema claimed otherwise.** Done. `Wallet` became `LedgerAccount` — a customer wallet is now one kind of account among float, transfer suspense, fee revenue, marketing expense, payout settlement and opening balance. | 44 | **Reading a system-account balance will get slow. Nothing reads one yet.** Balances are derived — sum the credits, subtract the debits — rather than stored. Measured on a million entries in a realistic distribution (20,000 wallets plus one float account carrying a leg for every movement): a **customer wallet is 0.4 ms** on an index-only scan, and **float is 720 ms** on a sequential scan. Float is slow because it is half the table, so an index on `accountId` narrows nothing and the planner correctly ignores it.
&nbsp;&nbsp;**Do not materialise customer wallets.** An earlier version of this entry recommended it; the measurement says otherwise. A customer's entry count grows with *their* activity, not the platform's — a heavy user reaches ~5,000 entries in a decade, still single-digit milliseconds — so storing the number would trade a performance problem we do not have for a correctness risk we do not have: a stored balance can drift from the entries, needing a reconciliation job to notice, and a bug in the update path corrupts a balance silently.
&nbsp;&nbsp;**Do not materialise float either.** Every transfer would run `UPDATE float SET balance = balance + x`, so every concurrent transfer queues on one row and total write throughput becomes the rate Postgres can serialise updates to a single tuple — a slow report traded for a cap on the whole product.
&nbsp;&nbsp;**When a reconciliation view is built:** cache the figure (recomputed on a timer, served from memory — it is a reconciliation number, not an authorisation input). Only if that is insufficient, snapshot rows plus a bounded scan of entries since the snapshot. **The trigger to revisit this early** is a payout integration needing "is there enough float to settle?" on the money path, which turns a background report into a hot-path read. | ⬜ |
| 45 | **The receive-currency side of a transfer is not in the ledger.** Send-currency movements are fully double-entry; the PKR (or INR) payout is recorded on the transfer row as `receiveAmount` and `fxRateApplied` and nowhere else. That is deliberate rather than unfinished: what the posting should look like depends on the payout partner’s settlement model — whether we prefund a local float account or they net against us — and guessing now would mean unpicking it later. Note that a posting cannot span currencies (the trigger rejects it, correctly): an exchange is two balanced postings linked by a rate, with the spread against an FX revenue account, not one posting with a CAD leg and a PKR leg. The transfer detail page states the boundary on screen. Do this with the provider integration. | ⬜ |
| 40 | **Staff cannot watch the queue over the socket.** `TransfersGateway` only joins `user:<id>`, so the operations queue polls on a 15-second timer. Now unblocked by the Redis adapter (#42) but still open, and the design matters more than the plumbing: staff must **not** subscribe to the firehose. At a thousand transfers a second, six events each, every staff browser would receive six thousand messages a second to render twenty rows — and an event about a transfer on page 40 of a filtered, sorted list is noise a stream cannot resolve anyway. The shape is: push aggregates (counts by status, overdue count) for the badge, push *invalidations* rather than rows so TanStack Query refetches the query it already has, and push detail only for the one transfer a detail page has joined. Role at handshake comes from a database read, not a JWT claim — `JwtStrategy.validate()` deliberately re-reads the user on every request so a demotion takes effect immediately, and a role in the token would give sockets a seven-day staleness window. | ⬜ |
| 41 | **The scheduler is a polling scan, and every replica runs its own.** Raised from a hard ceiling of ~2 transfers/second to a configurable batch worked by a bounded pool (#42), which buys room but not the right shape. Each replica scans the same rows; `advance()`'s compare-and-set means only one write lands, so it is safe and wasteful rather than wrong. The fix is claimed work — BullMQ on the same Redis — where a transition schedules the next as a delayed job instead of everything being rediscovered by a scan, workers scale horizontally, and retries and backoff stop being hand-rolled. Wants doing **with** the payout-provider integration, not before it: the mock advance logic is thrown away at that point and the queue shape is what the real provider's callbacks need anyway. | ⬜ |
| 42 | **The WebSocket layer could not survive a second instance.** Done. socket.io keeps rooms in the memory of the process that owns them, so a customer connected to replica A would receive nothing when the scheduler on replica B advanced their transfer — no error, no log, just a tracking screen that stops. `ScalableIoAdapter` shares rooms through Redis when `REDIS_URL` is set and is completely inert when it is not, so nothing needs provisioning today. Set the variable before scaling to two. Also fixed while here: both gateways declared `cors: { origin: true }` and accepted any origin at all, on the two endpoints that stream money movements — they now use the same allowlist as the HTTP API; and transports are pinned to websocket, because a long-polling handshake needs sticky sessions that Railway does not guarantee. Nine tests drive a real client over a real port, including that polling is refused and that an event never reaches another customer's socket. | ✅ |
| 46 | **The gateway origin allowlist blocked nothing for two commits.** Fixed. `a8f63f7` added a CORS allowlist to both WebSocket gateways and described it as closing a hole. It did not: socket.io’s `cors` option governs HTTP long-polling only, and the same commit pinned transports to WebSocket — which is exempt from the same-origin policy by design, so a browser sends `Origin` and then enforces nothing. Probed with a real client and a disallowed origin: it connected. The test passed the whole time because it asserted on the allowlist *function* rather than on the server, which is a test that can only ever confirm the author’s belief. Now enforced through `allowRequest`, which engine.io calls for every handshake, and tested through three real handshakes. **What actually protects those endpoints is the handshake token** — a bearer token in SecureStore or the OS keychain, not a cookie, so there is no ambient credential for a hostile page to ride on. Origin checking is defence in depth here, never the defence. | ✅ |

So the code written for “the day you scale to two instances” is itself unverified on the day it is needed. Before setting `REDIS_URL` in production, run two local instances against one Redis, connect a client to each, and confirm an event emitted on one reaches the other. That is a ten-minute check and it is the whole point of the change. | ⬜ |

**Why not Tauri's HTTP plugin**, which would avoid #26 entirely by issuing requests from
Rust where CORS does not apply: it gives the desktop build a different network stack from

Allowing the origin costs nothing real — this API authenticates with a bearer token rather
than a cookie, and `backend/src/main.ts` already records that CORS is not its access
